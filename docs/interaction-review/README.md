# Mushak settings interaction review

On the shipped build, shrinking the open shortcut editor to 720 × 360 pushed Save down to y=356. Only four of its 32 pixels fell inside the window. The panel itself ended at y=340 and clipped the whole button. The final build places it at y=299 through 331. Cancel and Save both work at that size. A separate Windows Settings process reopened the saved K assignment after restart.

The review stopped at the requested cap of 30 implementation rounds. The shipped baseline was a separate review.

5 of 14 groups reached a median Overall of at least 9 after 30 implementation rounds. The groups still below 9 are Shell and profile switcher, Button mapping list, Action editor and categories, Wheel button actions, Wheel settings, Gestures, Profiles and window capture, Device diagnostics, Conflict and feedback.

## Source and environment

The latest published GitHub release was [Mushak 0.0.11](https://github.com/divyangchauhan/Mushak/releases/tag/v0.0.11), dated 21 November 2026. The [release notes](../releases/0.0.11.md) identify the corresponding Store package as 1.0.11.0. I fetched remote branches and tags. The shipped tag points to `096d2c1693a3d390a7059dbd558aaa5274a05c88`. Its first parent, `44890726fc65b61f488b3dc8074c3dc56813a10b`, contains the settings redesign. Its second parent, `f8bcc6cfae3f06a634deb73312f1f6c18e82fe9a`, carries the earlier Store device fixes.

Fetched `origin/main` was `a1d161dc58795119f099aac7128fbc60084b788c`. Its merge base with the tag was `4489072`. Main did not contain the release merge. The release branch continued to `67b8150a1ad19588ffe25b0838a19f567ac895c0` with four Scoop and WinGet manifest edits. I based the isolated `design/interaction-review` worktree on the shipped tag so the baseline contains both parents. The original checkout and installed resident remained in place.

The GPU gallery uses the production Settings render and input paths with isolated sample settings. The normal client is 968 × 668 logical pixels, the compact client is 720 × 540, and the live-resize stress case is 720 × 360. Windows 26H2 build 26300.10075 reported 192 DPI, or 200%, on a 3000 × 1876 display. Settings captures are lossless WebP at logical resolution. The tray captures preserve native physical menu pixels. There was one active display scale. Dark and Light are the two Settings themes. Both use Marigold for these comparisons. The three optional accent values in the preferences file were not included. The native Windows menu rendered light even though Windows had both its application and system light-theme switches set to 0. The gallery records the actual menu appearance.

Each stage has a `captures.json` with dimensions, scale, theme and device state for each image. The connected 2S GUI replays a recorded Bluetooth report. The 3S, 4, extra control, generic USB mouse, missing device and conflict states use simulated reports. Mushak discovers the current mouse automatically. It has no device-selection menu. The availability of wheel, DPI and gesture controls follows the reported capabilities.

A separate read-only diagnostic identified the **physical** Wireless Mouse MX Master 2S over Bluetooth, at 1000 DPI, with four remappable controls. In one discovery pass the mouse omitted DPI support. A read twelve seconds later returned the DPI capability and 1000 DPI. The [physical device readings](physical-device.json) record both. All remapping, DPI and gesture interactions below use isolated sample settings. Physical button actuation, on-device wheel-mode changes and gesture recognition were not verified in this review.

## Independent reviews

OpenAI `gpt-6.2-astra` implemented the changes and had no vote. The reviewers were `gpt-6.2-sol`, `gpt-6.1-terra` and `gpt-6-astra`. Each reviewed a neutral, single-version packet in a fresh context. They opened the actual rendered pixels, including both themes and ordered shortcut frames in both themes. They did not receive a target, stage number, prior score or another reviewer's comments. The fixed anchors were 8 for a good screen with a material issue, 9 for excellent and 10 for exceptional.

Every stage has 42 ballots. For rounds 5 through 10, the live councils inspected all 14 groups and scored each changed group. Separate blind passes later scored the archived, unchanged groups from those rounds. Each reviewer received the six anonymized historical packets in a different order and graded each on its own. The CSV identifies these retrospective ballots. All 1302 group ratings use the actual stage pixels. Each ballot includes eight scores, a visible label, a specific detail and any remaining concern.

The six individual tab switches can also be replayed in the ordered gallery, in both themes, using real Windows Settings processes. For the shipped side I downloaded the published mushak.exe and matched its SHA-256, aecf312a4a89909b372186a0bbb1c594b46b968c86b419b785ef540149235f7f. All three reviewers separately inspected those twelve extra captures. Their [supplementary observations and scores](baseline/native-cycle-reviews.json) do not replace the baseline ballots. The final panel received every group at its original logical capture resolution. The gallery also shows all five Settings sections at 720 × 540 from the published and worktree executables, in both themes. The [separate blind review of the ten shipped compact frames](baseline/native-compact-reviews.json) supplements the original baseline ballots. In both themes the full native frames for the three visits to Actions were pixel-identical, as were the three visits to Keyboard shortcut, on both the published and worktree builds.

In round 30 I compared the region containing the first mapping before and after opening the two-profile chooser. All 13,000 sampled pixels matched in both themes. The first round-4 capture of the paused tray had a rendering artifact. All three reviewers inspected the replacement pixels before their tray votes were counted. ## Validation and limits

- `cargo test --locked` passed all 62 tests. Coverage includes legacy config, capability gates, connected and offline mappings and gesture inheritance.
- `cargo clippy --locked --all-targets` exited successfully with warnings. They include picker style warnings and an MSRV warning in the existing high-resolution wheel code.
- `cargo build --release --locked` succeeded. The separate Windows process test started the release executable with `--settings` and temporary APPDATA, sent pointer and keyboard messages, checked the active application's saved mapping and launched Settings again.
- `cargo run --locked -- --ui-smoke` passed the GPU interaction suite, including all five gestures, MX Master generations and variants, discrete DPI choices, native wheel assignment, scroll bounds and offline editing. `--ui-smoke --review-gallery` and its `--more-states` variant regenerate the paired GPU states.
- The GPU interaction check opened and canceled the foreground-window countdown in both themes. A separate Windows process test let the countdown finish over a temporary Python window, verified its foreground PID, and confirmed that only its executable name was added to Preview app. It removed that executable, added a new profile, removed it, and checked that the entire sample configuration returned to its prior contents. Runs that required the Python window to remain in front were discarded when focus moved. In round 20 I also checked what happens when a user switches applications during the countdown. The runner observed the foreground executable through Windows and compared it with the saved value. Mushak selected brave.exe, the active application at expiry, and removed it again when clicked. The captures show only the Mushak window. The launcher waits for the expected window size and theme before clicking the profile switcher. In round 22 a compact click landed on the open profile chooser. Miniquad handles a Windows button message at the position of the last mouse move. The native runner now sends the target position directly before both button messages and waits for the expected navigation highlight and heading. Fresh compact runs passed on the normal and three-profile fixtures in both themes. Terminating a real conflicting driver, changing Windows startup, the system clipboard output of the diagnostic copy commands and the tray's live battery tooltip are unverified. The standalone tray runner reproduced the two round-21 native menu captures at 383 × 202 physical pixels. The largest difference in any RGB channel was one level out of 255.
- Gallery renders use scripted mouse events in the production UI. The native process sequence separately checks normal Windows mouse and key delivery. Short screenshot sequences cannot measure continuous frame pacing. There was no second active Windows display scale to compare. The repository-wide format check reports differences in the action preset list and logging module. Both files also differed from rustfmt on the unmodified release tag.

On the baseline, the native process test canceled at normal size. The short-window failure is visible in the paired GPU sequence. On the final worktree build the Windows process test clicked both Cancel and Save inside the 720 × 360 window. With M pending it also switched to Actions and back, matched the original key pixels and verified the configuration was untouched before Cancel. The first native resume test reproduced a [stale Settings window](evidence/idle-before.webp) twice. Its [capture conditions](evidence/idle-before.json) record the four-second wait. The resident changed to paused, but the blocking Settings event loop slept until the next input. A one-second Windows timer now wakes the visible Settings window. It clicks Resume, receives the signal in the test process and checks that Settings removes the badge only after the test resident publishes the active state.
